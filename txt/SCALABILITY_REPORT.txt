1. EXECUTIVE SUMMARY
================================================================================

With 1000 concurrent users uploading videos/reels and watching content on cPanel,
the platform WILL experience severe slowdowns and likely errors. The three biggest
threats are:

  - Video uploads blocking the entire server for 30-120+ seconds each
  - Session and cache both hitting the same MySQL database on every single request
  - Homepage and reels pages running 15-50+ uncached database queries per load

With 1000 users, this means 10,000-50,000+ raw MySQL queries per minute just for
page loads, plus FFmpeg transcoding locking PHP workers during uploads.

================================================================================
2. CRITICAL BOTTLENECKS (P0) - WILL CAUSE ERRORS OR COMPLETE SLOWDOWN
================================================================================

ISSUE #1: SYNCHRONOUS VIDEO TRANSCODING
----------------------------------------
  Location:  config/queue.php (.env: QUEUE_CONNECTION=sync)
             app/Services/Frontend/VideoService.php line 536
             ProcessVideo job

  Problem:   The queue is set to "sync", meaning ALL jobs run inside the HTTP
             request. When a user uploads a video, FFmpeg transcodes it into
             3 HLS variants (360p, 720p, 1080p) SYNCHRONOUSLY inside their
             browser request. This blocks the PHP worker for 30-120+ seconds.

             The code at VideoService.php:536 uses dispatchSync() which forces
             synchronous execution even if the queue were changed.

             The CompressReel job has a $timeout of 300 seconds (5 minutes)
             and does FFmpeg compression + BunnyCDN upload synchronously.

  Impact:    If 50 users upload videos simultaneously, 50 PHP-FPM workers are
             locked for 30-120 seconds. cPanel typically has 10-30 PHP workers.
             The server will stop responding to ALL requests (watching, browsing,
             everything) until uploads finish. 502/504 errors are guaranteed.

  Verdict:   THIS IS THE #1 KILLER. Uploading videos will crash the server.


ISSUE #2: DATABASE SESSIONS THAT NEVER EXPIRE
----------------------------------------------
  Location:  config/session.php (.env: SESSION_DRIVER=database, SESSION_LIFETIME=525600)

  Problem:   Every single HTTP request reads from AND writes to the MySQL
             "sessions" table (2 DB queries per request minimum). Sessions are
             set to last 525600 minutes (1 YEAR) and never truly expire.

             With 1000 concurrent users, the sessions table grows by ~1000 rows
             and is never cleaned. After 1 month: ~30,000 rows. After 6 months:
             ~180,000 rows. Every SELECT and UPDATE on this table gets slower.

             The session sweep lottery (2% chance per request) is effectively
             useless when sessions last a year.

  Impact:    Every page load = 2 extra MySQL queries on a table that grows
             forever. With 1000 users = 2000 queries/minute on sessions alone.
             Over months, this table becomes a major drag on MySQL.


ISSUE #3: CACHE STORED IN MYSQL DATABASE
-----------------------------------------
  Location:  config/cache.php (.env: CACHE_STORE=database)

  Problem:   The cache driver is set to "database", meaning every Cache::get()
             and Cache::put() is a MySQL SELECT/INSERT/UPDATE query. This
             defeats the entire purpose of caching.

             The gs() helper (GeneralSetting) is called on almost every page
             and hits the database cache table every time.

             The UpdateLastSeen middleware does Cache::put() for every user
             every request = 1000 writes/minute to the cache table.

  Impact:    Instead of sub-millisecond in-memory cache lookups, every cache
             operation takes 5-50ms from MySQL. With 1000 users making multiple
             requests, this adds seconds of cumulative latency per minute.

  Note:      Some parts of the code already work around this by hardcoding
             Cache::store('file') but this is inconsistent.

3. HIGH PRIORITY ISSUES (P1) - WILL CAUSE SIGNIFICANT SLOWDOWN
================================================================================

ISSUE #4: ORDER BY RAND() ON HOMEPAGE QUERIES
----------------------------------------------
  Location:  app/Services/Frontend/HomeService.php

  Problem:   The homepage uses inRandomOrder() on 6+ different queries. MySQL's
             ORDER BY RAND() requires scanning the ENTIRE result set, assigning
             random values to every row, then sorting - this is O(n) on every
             request. With large video tables, this is extremely expensive.

             The trending query fetches 20 rows, shuffles them in PHP, then
             takes 12 - doubly wasteful.

  Impact:    6 full-table-scan random queries per homepage load. With 1000 users,
             this is 6000 expensive queries/minute hitting MySQL.


ISSUE #5: HOMEPAGE RUNS 15-18 UNCACHED QUERIES PER LOAD
---------------------------------------------------------
  Location:  app/Services/Frontend/HomeService.php (getHomepageData)

  Problem:   Every homepage load executes these queries with NO caching:

    1.  Videos paginated (12)          + count query
    2.  Trending videos (20 -> 12)     + count with viewLogs subquery
    3.  Featured videos (12)
    4.  Featured channels (12)         + user eager load
    5.  Reels (12)                     + user.channel eager load
    6.  Featured actors (10)           + 2 aggregate queries
    7.  Featured influencers (10)      + 2 aggregate queries
    8.  Featured investors (10)        + 2 aggregate queries
    9.  4 Banner ad queries

  Total: ~15-18 queries, each with heavy eager loading and subqueries.

  Impact:    1000 users = 15,000-18,000 MySQL queries per minute from homepage
             alone. Each query includes JOINs, subqueries, and aggregations.


ISSUE #6: REELS PAGE EAGER-LOADS SUBSCRIBERS
---------------------------------------------
  Location:  app/Services/Frontend/ReelService.php line 86

  Problem:   The reels page eager-loads "channel.subscribers" for every reel.
             If a reel's channel has 10,000 subscribers, that's 10,000 rows
             loaded into memory per reel. With 50 reels, this could mean
             loading millions of rows.

  Additionally: The Blade template (reels/index.blade.php line ~1495) calls
    $r->channel?->subscribers()->count() for each reel, which runs a COUNT
    query per reel instead of using the eager-loaded collection count.

  Impact:    50 extra COUNT queries per reels page load. With 1000 users
             browsing reels = 50,000 extra queries/minute.


ISSUE #7: NO REDIS/MEMCACHED ON CPANEL
----------------------------------------
  Problem:   cPanel shared hosting typically does not provide Redis or Memcached.
             Since sessions, cache, and queue all depend on MySQL, the database
             becomes a single massive bottleneck handling everything at once.

  Impact:    MySQL must handle application data queries + sessions + cache +
             queue jobs simultaneously. This will hit the MySQL connection limit
             (typically 150-256 on shared cPanel) very quickly.

4. MEDIUM PRIORITY ISSUES (P2) - WILL DEGRADE USER EXPERIENCE
================================================================================

ISSUE #8: EXTERNAL API CALL ON EVERY VIDEO VIEW
-------------------------------------------------
  Location:  app/Services/Frontend/VideoService.php (app()->terminating callback)

  Problem:   Every video page load triggers getIpInfo() which makes an external
             HTTP API call to determine the viewer's country for analytics.
             This adds 100-500ms of network latency to every single video view.

  Impact:    1000 users watching videos = 1000 outbound HTTP requests adding
             latency. If the GeoIP service is slow or down, video views hang.


ISSUE #9: 610KB+ BLOCKING EXTERNAL SCRIPTS ON VIDEO PAGE
---------------------------------------------------------
  Location:  resources/views/frontend/videos/show.blade.php lines 3-14, 256-257

  Problem:   Before any content renders, the video page loads these blocking
    resources (no defer/async):
    - Plyr CSS (~30KB)
    - HLS.js (~250KB)
    - Plyr JS (~100KB)
    - Material Symbols font (~100KB)
    - Font Awesome CSS (~80KB)
    - Additional fonts and styles

  Impact:    Slow First Contentful Paint. Users see a blank screen for 1-3
             seconds while 610KB+ of render-blocking resources download.


ISSUE #10: VIDEO DOWNLOADS PROXIED THROUGH PHP
-----------------------------------------------
  Location:  VideoController::download() (curl streaming through PHP)

  Problem:   When users download videos, the request goes through the Laravel
             server which streams the file via curl. This occupies a PHP-FPM
             worker for the entire download duration.

  Impact:    100 concurrent downloads = 100 PHP workers blocked. The server
             stops responding to all other requests.


ISSUE #11: UNBOUNDED COMMENT REPLIES
--------------------------------------
  Location:  app/Services/Frontend/VideoService.php lines 116-122

  Problem:   Top-level comments are limited to 20, but each comment eager-loads
             ALL replies without a limit. A viral video with 500 replies on a
             single comment loads all 500 + their user models.

  Impact:    Memory exhaustion and slow queries on popular videos.


ISSUE #12: BLADE TEMPLATES INLINE QUERIES
-------------------------------------------
  Location:  resources/views/frontend/videos/show.blade.php lines 549-557, 601-603

  Problem:   The video show template runs these queries inline:
    - Subscription::where()->exists() for subscribe status
    - Playlist query for Watch Later check
    - Another Subscription query for notification preference
    - $video->user->channel->subscribers_count (lazy load)

  Impact:    ~5 extra DB queries per video page view that could be loaded
             in the controller with eager loading.

6. TEMPLATE-SPECIFIC ANALYSIS
================================================================================

--- resources/views/frontend/reels/index.blade.php ---

  Severity: CRITICAL

  Key Findings:
  - 50 reels loaded with 9 eager relations + 3 count subqueries each
  - 50 extra COUNT queries from subscribers()->count() in Blade
  - 1200-line inline script block with ~50KB of embedded JSON state
  - HLS.js loaded as blocking script (no defer/async)
  - Up to 7 concurrent HLS players created as user scrolls
  - Videos served from BunnyCDN (good) but local fallback exists (bad)

  Query Estimate Per Page Load: ~55-60 MySQL queries


--- resources/views/frontend/videos/show.blade.php ---

  Severity: HIGH

  Key Findings:
  - 610KB+ of render-blocking external resources before content
  - 3 inline @php queries in the Blade template (subscription, playlist)
  - Unbounded comment replies loaded without limit
  - getIpInfo() external API call on every view via app()->terminating
  - 10+ related videos loaded on each page
  - Ad system checks run on every timeupdate event

  Query Estimate Per Page Load: ~25-30 MySQL queries


--- resources/views/frontend/index.blade.php ---

  Severity: HIGH

  Key Findings:
  - 15-18 database queries on every load with NO page-level caching
  - 6 queries use ORDER BY RAND() (full table scans)
  - Up to 135 partial renders (video_card, channel_card, creator_card)
  - 4 continuous requestAnimationFrame animation loops
  - Infinite scroll uses file cache (not shared across PHP workers)
  - 5 <video> elements preloaded with metadata
  - $reels->count() forces full collection evaluation unnecessarily

  Query Estimate Per Page Load: ~15-18 MySQL queries

7. RECOMMENDED FIXES (PRIORITY ORDER)
================================================================================

FIX #1 - HIGHEST IMPACT (Fixes P0 #1):
  Change QUEUE_CONNECTION=database in .env
  Change ProcessVideo::dispatchSync() to ProcessVideo::dispatch() in
    VideoService.php line 536
  Set up "php artisan queue:work --timeout=300" as a cPanel cron job
  This alone prevents server crashes from concurrent uploads.

FIX #2 - HIGH IMPACT (Fixes P0 #2):
  Change SESSION_DRIVER=file in .env
  Change SESSION_LIFETIME=120 in .env (2 hours, not 1 year)
  This eliminates 2 MySQL queries per request for sessions.

FIX #3 - HIGH IMPACT (Fixes P0 #3):
  Change CACHE_STORE=file in .env
  This eliminates all cache-related MySQL queries.

FIX #4 - HIGH IMPACT (Fixes P1 #4, #5):
  Add Cache::remember() with 60-second TTL around HomeService::getHomepageData()
  Replace inRandomOrder() with cached random IDs or useRandSeeder patterns
  This cuts homepage queries from 15-18 to 1 per minute per user.

FIX #5 - MEDIUM IMPACT (Fixes P1 #6):
  Remove "channel.subscribers" from ReelService eager loading
  Use $reel->channel->subscribers->count() (collection count) instead of
    ->subscribers()->count() (DB query) in the Blade template

FIX #6 - MEDIUM IMPACT (Fixes P2 #8):
  Move getIpInfo() and view counting to a queued job
  This removes external API latency from video page loads.

FIX #7 - LOW EFFORT (Fixes P2 #9):
  Add defer or async to HLS.js and Plyr script tags
  Load fonts with display=swap

FIX #8 - MEDIUM EFFORT (Fixes P1 #7):
  If possible, request Redis access from cPanel provider or use Cloudflare
  as a reverse proxy for static assets.
