2. WHAT CHANGED AFTER THE FAST-UPLOADING WORK (DELTA SUMMARY)
================================================================================

BEFORE FAST UPLOADING:
  - Uploads streamed THROUGH the server (browser -> PHP -> BunnyCDN)
  - One 2GB upload could occupy a PHP worker + bandwidth for an hour
  - 20 concurrent uploads = server freeze for everyone

AFTER FAST UPLOADING (current state):
  - Uploads go browser -> BunnyCDN directly (TUS protocol)
  - Server only creates the video record + signs TUS params (~2 queries)
  - Server bandwidth cost of uploads: ZERO
  - Encoding handled by BunnyCDN, webhook flips status when done
  - FFmpeg local processing only runs for legacy/local files,
    and even that is queued (ProcessVideo async)

COMBINED WITH THE OTHER FIXES:
  - Sessions/cache moved off MySQL (file driver)
  - Homepage fully cached (2-3 queries vs 15-18)
  - Views/notifications/logging moved to background queue
  - Reels page stripped of subscriber mass-loading

2b. HOW IT WORKS NOW - STEP BY STEP FLOWS (AFTER ALL CHANGES)
================================================================================

FLOW A: USER UPLOADS A VIDEO (1k users uploading at once)
------------------------------------------------------------------------
  1. User picks file on upload page
  2. Browser calls POST /videos/prepare-upload  (throttle:upload)
     -> Server creates video row + Bunny video entry, signs TUS params
     -> Server cost: ~4 fast queries. NO file bytes touch the server.
  3. Browser uploads 10MB chunks DIRECTLY to BunnyCDN (TUS protocol)
     -> Network drop? Upload auto-resumes from last chunk.
     -> Retry delays: 0s, 3s, 5s, 10s, 20s
     -> Server load during entire upload: ZERO
  4. Thumbnail uploaded separately to server (small file)
  5. BunnyCDN encodes the video in the cloud (720p/1080p)
  6. BunnyCDN calls POST /webhooks/bunny when done
     -> Video auto-published, subscribers notified via QUEUE (async)
  7. Frontend polls checkStatus -> shows "ready" to the uploader

  RESULT: 100 users uploading 2GB files simultaneously = server feels
  almost nothing. This was the crash scenario before; now impossible.

FLOW B: USER UPLOADS A REEL
------------------------------------------------------------------------
  Same as Flow A but uses POST /reels/prepare-upload and the reel
  Bunny library. Compression of legacy/local reels runs as queued
  CompressReel job - never blocks a web request.

FLOW C: USER WATCHES A VIDEO (1k users watching at once)
------------------------------------------------------------------------
  1. GET /videos/{slug} -> controller -> VideoService::getVideoData()
  2. Page data queries run (comments limited to top 20)
  3. AFTER response is sent (terminating callback):
     - views_count incremented (single fast UPDATE)
     - RecordVideoView job pushed to queue
  4. Queue worker later does GeoIP lookup + writes ViewLog row
     -> Slow GeoIP API call NEVER delays the viewer's page
  5. Actual video streams from BunnyCDN edge servers, NOT from VPS
     -> 1k concurrent streams = 0 VPS bandwidth

  RESULT: Watching is read-mostly + CDN-delivered. Scales easily.

FLOW D: USER LIKES A VIDEO/REEL/COMMENT
------------------------------------------------------------------------
  1. POST like toggle -> one indexed SELECT + INSERT or DELETE
  2. Counter updated, fresh count returned as JSON
  3. WebSocket broadcast wrapped in try/catch
     -> Even if Reverb WebSocket server is DOWN, the like still
        succeeds silently (only a log line). Verified in code.

FLOW E: USER COMMENTS
------------------------------------------------------------------------
  1. POST comment -> keyword filter reads cached list (file cache,
     refreshed hourly) - no DB scan
  2. Single INSERT into comments table
  3. Reply/mention/video-owner notifications dispatched to QUEUE
     -> Firebase push sends happen in background workers
  4. Comment page shows max 20 top-level comments (memory safe)

FLOW F: 1k USERS OPEN THE HOMEPAGE AT THE SAME SECOND
------------------------------------------------------------------------
  1. First request after cache expiry rebuilds data (~15 queries)
  2. All other 999 requests read pre-built data from FILE cache
     -> ~2-3 DB queries total per minute for the whole homepage
  3. Sessions from files, settings from file cache
     -> MySQL stays idle; page loads in under a second

5. REQUIRED PRODUCTION DEPLOYMENT STEPS (DO NOT SKIP)
================================================================================

  CRITICAL - without step 1, NOTHING queued will ever run
  (video processing, view logs, notifications all sit in the jobs table):

  Step 1: Queue worker cron on the VPS (cPanel > Cron Jobs):
      * * * * * cd /home/USER/public_html && php artisan queue:work
                --sleep=3 --tries=2 --max-time=3600 >> /dev/null 2>&1

  Step 2 (recommended): Install Redis, then in .env:
      QUEUE_CONNECTION=redis
      CACHE_STORE=redis
      SESSION_DRIVER=redis
      php artisan config:cache
      (config/queue.php already has retry_after=660 for redis - verified)

  Step 3: Start Reverb WebSocket for real-time notifications:
      php artisan reverb:start --host=0.0.0.0 --port=8080 &
      (likes/comments still work if Reverb is down - verified try/catch)

  Step 4: BunnyCDN dashboard: keep only 720p + 1080p encoding profiles,
          enable Fast Encode.
