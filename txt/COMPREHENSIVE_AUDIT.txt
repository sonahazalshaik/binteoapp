3. P0 CRITICAL ISSUES (SERVER CRASHERS)
================================================================================

ISSUE #1: SYNCHRONOUS VIDEO TRANSCODING
-----------------------------------------
  Location:  app/Services/Frontend/VideoService.php:536
             app/Jobs/ProcessVideo.php

  Code:      ProcessVideo::dispatchSync($video);

  Problem:   FFmpeg transcodes video into 3 HLS variants (360p, 720p, 1080p)
             SYNCHRONOUSLY inside the HTTP request. Blocks PHP worker for
             30-120+ seconds. ProcessVideo implements ShouldQueue but is
             called with dispatchSync(), bypassing the queue entirely.

  The ProcessVideo job has NO $timeout property (defaults to 60s) but FFmpeg
  transcoding can take 30-120+ seconds for large videos.

  Note: Admin panel dispatches it correctly with ProcessVideo::dispatch()
  (ManageVideoController.php:166, Admin/VideoController.php:243)

  Impact:    50 simultaneous uploads = 50 PHP workers locked for minutes.
             cPanel/VPS typically has 10-30 PHP workers. Server stops
             responding to ALL requests. 502/504 errors guaranteed.


ISSUE #2: DIRECT VIDEO/REEL UPLOADS BLOCK PHP WORKERS
------------------------------------------------------
  Location:  app/Services/Frontend/UploadService.php:480-495
             app/Services/Frontend/UploadService.php:541-560

  Code:      set_time_limit(0);
             $fileContent = file_get_contents($file->getRealPath());
             Http::withBody($fileContent)->put("https://video.bunnycdn.com/...");

  Problem:   Reads entire video file into memory, then uploads to Bunny CDN
             via synchronous HTTP PUT with 3600 second (1 HOUR) timeout.
             Each upload holds a PHP worker for the entire duration.

  Impact:    10 concurrent uploads = 10 PHP workers blocked for minutes each.


ISSUE #3: TUS PROXY CHUNK UPLOADS BLOCK WORKERS
-------------------------------------------------
  Location:  app/Http/Controllers/TusProxyController.php:75-78

  Code:      Http::patch()->timeout(120)  // per chunk

  Problem:   Every upload chunk is proxied through PHP with 120s timeout.
             Each chunk holds a worker for up to 2 minutes.

  Impact:   Upload chunks are frequent. Multiple simultaneous uploads
             will exhaust PHP workers.


ISSUE #4: VIDEO DOWNLOADS PROXIED THROUGH PHP
----------------------------------------------
  Location:  app/Http/Controllers/Web/VideoController.php:59-83

  Code:      set_time_limit(0);
             $ch = curl_init();
             curl_setopt($ch, CURLOPT_WRITEFUNCTION, function(...) {
                 echo $data; flush();
             });
             curl_exec($ch);

  Problem:   Downloads stream from Bunny CDN through PHP via cURL proxy.
             Each download holds a PHP-FPM worker for the ENTIRE transfer.
             A 500MB video download could hold a worker for minutes.

  Impact:    100 concurrent downloads = 100 PHP workers blocked.


ISSUE #5: DATABASE SESSIONS THAT NEVER EXPIRE
----------------------------------------------
  Location:  .env: SESSION_DRIVER=database, SESSION_LIFETIME=525600

  Problem:   Every request reads/writes the MySQL sessions table (2 queries).
             Sessions last 525600 minutes (1 YEAR). Table grows unbounded.
             After 1 month: ~30,000 rows. After 6 months: ~180,000 rows.

  Impact:    2 extra MySQL queries per request. Over months, sessions table
             becomes a major drag on MySQL performance.


ISSUE #6: CACHE STORED IN MYSQL DATABASE
-----------------------------------------
  Location:  .env: CACHE_STORE=database

  Problem:   Every Cache::get() and Cache::put() is a MySQL query.
             This defeats the entire purpose of caching.

  Note:      Some code works around this with Cache::store('file') but
             the global default still hits MySQL.

  Impact:    Instead of sub-millisecond in-memory cache, every cache
             operation takes 5-50ms from MySQL.


ISSUE #7: SUBSCRIBER NOTIFICATION FAN-OUT (SYNCHRONOUS)
--------------------------------------------------------
  Locations: app/Services/Frontend/VideoService.php:502-528
             app/Services/Frontend/UploadService.php:389-413
             app/Services/Frontend/ReelService.php:415-441
             app/Http/Controllers/BunnyWebhookController.php:110-135

  Problem:   When a video is published, code loops over ALL subscribers
             and for EACH subscriber:
               1. Creates a UserNotification DB record (INSERT)
               2. Broadcasts via Reverb WebSocket
               3. Dispatches SendFirebaseNotificationJob

             For a channel with 10,000 subscribers: 10,000 DB inserts +
             10,000 broadcasts + 10,000 job dispatches SYNCHRONOUSLY.

  Impact:    A single video publish from a large channel can take minutes
             and create 30,000+ synchronous operations.

ISSUE #8: ORDER BY RAND() EVERYWHERE
--------------------------------------
  Locations: app/Services/Frontend/HomeService.php:20,65,70,75
             app/Services/Frontend/ReelService.php:122,131,165

  Problem:   inRandomOrder() = ORDER BY RAND() = full table scan.
             Homepage has 4x inRandomOrder().
             Reels page has 3x inRandomOrder().

  Impact:    1000 users = 7000 full-table-scan queries/minute.
             With large tables, each query can take 100-500ms.


ISSUE #9: ZERO CACHING ON HOMEPAGE/VIDEO/CHANNEL PAGES
--------------------------------------------------------
  Locations: app/Services/Frontend/HomeService.php:15-88 (12 queries)
             app/Services/Frontend/VideoService.php:35-170 (15+ queries)
             app/Services/Frontend/ChannelService.php:21-47 (7+ queries)

  Problem:   Every page load runs all queries fresh against MySQL.
             Homepage: 12 separate queries with JOINs and subqueries.
             Video page: 15+ queries with eager loading.
             Channel page: 7+ queries, some loading overlapping data.

  The ONLY cache in the web frontend is HomeService::fetchVideos() which
  uses Cache::store('file')->remember() with 30s TTL for AJAX load-more.

  Impact:    1000 users = 12,000-18,000 MySQL queries/minute for homepage alone.


ISSUE #10: REELS PAGE EAGER-LOADS SUBSCRIBERS
------------------------------------------------
  Location:  app/Services/Frontend/ReelService.php:86

  Code:      $query->with(['user.channel', 'music', 'hashtags', 'likes',
             'channel', 'channel.subscribers', 'category'])

  Problem:   Loads ALL subscribers for every reel's channel. If a channel
             has 10,000 subscribers, that's 10,000 rows per reel.
             With 50 reels = potentially 500,000 rows loaded into memory.

  Then at reels/index.blade.php:1495:
    subscribers_count: {{ $r->channel?->subscribers()->count() ?? 0 }}
  This runs a COUNT query per reel INSTEAD of using the eager-loaded data.

  Impact:    Massive memory usage + 50 extra COUNT queries per page load.

9. JOB & QUEUE AUDIT
================================================================================

--- ProcessVideo.php ---
  Implements ShouldQueue BUT called with dispatchSync()
  No $timeout property (default 60s)
  No $tries property (default 3)
  Processing: FFmpeg HLS transcoding (360p, 720p, 1080p)
  Risk: BLOCKS HTTP worker for minutes

--- CompressReel.php ---
  Implements ShouldQueue, called with dispatch() (async) CORRECT
  $timeout = 300 (5 minutes)
  $tries = 3
  Processing: FFmpeg compression + BunnyCDN upload
  Risk: Properly configured

--- SendFirebaseNotificationJob.php ---
  Implements ShouldQueue, called with dispatch() (async) CORRECT
  No $timeout (default 60s)
  No $tries (default 1 - no retries!)
  Processing: Firebase HTTP API call
  Risk: Slow Firebase = silent failures, no retries

  Dispatched from 17 locations across the codebase

--- Queue Configuration ---
  QUEUE_CONNECTION=sync (ALL jobs run synchronously in HTTP request)
  Scheduler runs: queue:work --stop-when-empty --tries=3 --timeout=300 (every minute)
  This is a WORKAROUND for no persistent queue worker - very inefficient

14. SERVER SIZING RECOMMENDATIONS (1000 CONCURRENT USERS)
================================================================================

--- Minimum Cloud VPS Specs ---
  CPU:       4+ cores (8 recommended for FFmpeg)
  RAM:       8GB minimum (16GB recommended)
  Storage:   NVMe SSD, 100GB+
  Network:   1Gbps+
  PHP:       PHP 8.2+ with OPcache enabled
  MySQL:     8.0+ with InnoDB, max_connections=500
  Web:       Nginx (not Apache mod_php)

--- PHP-FPM Configuration ---
  pm.max_children = 50       (adjust based on RAM)
  pm.start_servers = 10
  pm.min_spare_servers = 5
  pm.max_spare_servers = 20
  pm.max_requests = 500      (recycle workers)

--- MySQL Configuration ---
  innodb_buffer_pool_size = 4G  (50% of RAM)
  max_connections = 500
  query_cache_type = 0          (disabled for MySQL 8)
  slow_query_log = 1
  long_query_time = 1

--- Queue Worker ---
  php artisan queue:work --timeout=300 --tries=3 --max-time=3600
  Run as persistent systemd service (NOT cron every minute)

--- OPcache ---
  opcache.enable=1
  opcache.memory_consumption=256
  opcache.max_accelerated_files=20000
  opcache.validate_timestamps=0  (in production)

--- Nginx ---
  worker_processes auto
  worker_connections 1024
  keepalive_timeout 65
  client_max_body_size 500M     (for video uploads)
  gzip on
  gzip_types text/css application/javascript application/json

--- Optional: Redis (if available) ---
  Install Redis for cache + sessions + queue
  CACHE_STORE=redis
  SESSION_DRIVER=redis
  QUEUE_CONNECTION=redis
  This is the single biggest performance improvement after fixing code.

--- Static Assets ---
  Serve via Nginx directly (not PHP)
  Set proper Cache-Control headers
  Enable Brotli/Gzip compression
  Use CDN for CSS/JS if possible

--- Monitoring ---
  Install: htop, mytop, netdata, or New Relic
  Monitor: PHP-FPM pool, MySQL connections, disk I/O, memory
  Alert on: >80% CPU, >80% RAM, >100 MySQL connections
