1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Current architecture: Browser -> same-origin /tus-proxy (Laravel) -> Bunny TUS.
Fallback: Browser -> server direct-upload -> Bunny PUT. Encoding is done by
Bunny Stream; Laravel queues handle only legacy/local processing.

CRITICAL FINDING: POST /tus-proxy was returning HTTP 419 (CSRF) because the
CSRF exclusion pattern 'tus-proxy/*' did not match the bare create URL.
Verified live during this investigation. This alone breaks every proxied
upload at step 1 and best explains intermittent total upload failures.

The "re-upload same video fails" symptom is NOT caused by chunking, the proxy
concept, or queues. Backend fully supports re-uploads (new DB row + new Bunny
GUID every attempt, nothing reused). Root cause candidates found in code:
  a) File input value never reset -> selecting SAME file again fires no
     change event (frontend no-op). [was missing, now fixed]
  b) No double-submit guard on startUpload(). [now fixed]
  c) CSRF 419 on proxy CREATE. [now fixed]
  d) Old proxy 409 handling resent full chunks at wrong offsets. [now fixed]

7. 409 INVESTIGATION
--------------------------------------------------------------------------------
Generated by ..... Bunny (offset mismatch vs stored bytes). App never
                   generates 409 itself.
Old handling ..... resent the ENTIRE chunk at whatever HEAD offset returned
                   -> corruption risk / loops. DEFECTIVE (rewritten).
New handling ..... HEAD Bunny -> reconcile:
                   offset==client        -> retry whole chunk
                   client<offset<client+len -> send remainder slice only
                   offset>=client+len    -> return 204 (already stored)
                   offset<client or non-numeric (e.g. "2") -> HTTP 400 +
                   Log::critical -> frontend stops retrying -> fallback.
Retry bound ...... tus-js-client retryDelays cap at 5 attempts; 400 is
                   non-retryable. Infinite loops impossible.
New upload after 409? NO - never creates another Bunny video.
Upload-Offset:"2" . Local laravel.log contains ZERO TUS/409 entries (only
                   local dev noise); production logs required. Code review:
                   proxy never fabricates offsets; frontend only reads what
                   proxy forwards. Most plausible origin: stale/duplicate TUS
                   session against one GUID from the pre-proxy era where
                   retry loops reused video IDs. VERDICT: UNKNOWN until prod
                   logs captured; now fully instrumented (structured events).

8. SAME-VIDEO CONCURRENT UPLOAD INVESTIGATION
--------------------------------------------------------------------------------
Upload #1: filename A.mp4 -> local Video id N, Bunny GUID G1, TUS id/url
           derived from G1, random fingerprint F1, bunny_status uploading->
           processing->ready.
Upload #2: startUpload() runs prepare-upload AGAIN -> NEW row id M, NEW GUID
           G2, NEW signature/URL, NEW random fingerprint F2, NEW state.
COMPARISON: NOTHING is shared. No reuse of JS object, tus object, bunny_id,
URL, offset, fingerprint, or state. tus.Upload is constructed fresh inside a
per-attempt Promise. Database has NO unique index on bunny_id (plain index,
migration 2026_04_27_100000) and slug collisions are resolved with random
suffixes. No validation blocks duplicate titles/filenames. No upload locks
exist that would reject a second upload while the first processes.
=> Backend officially SUPPORTS re-upload of A.mp4.
Actual historical failure causes identified: (a) input.value not reset ->
change event never fired on same-file reselect (looks exactly like "second
upload fails" to the user); (b) double-execution without guard; (c) 419 on
proxy CREATE; all addressed. Also note throttle:upload = 100 req/hour/user -
rapid repeated attempts can produce 429s.

9. BUNNY PROCESSING FLOW
--------------------------------------------------------------------------------
uploading -> processing (Bunny status 1,2,3) -> ready (status 4 or
encodeProgress>=100) -> error (5,6). Checked via GET status endpoints
(UploadService::checkStatus/checkReelStatus) and webhook /webhooks/bunny
(web.php:648). scopePublished/scopeForChannelFeed require bunny_status='ready'
so unfinished copies are invisible publicly. A video being processed CANNOT
block another upload - there is no cross-record dependency.

10. DATABASE INVESTIGATION
--------------------------------------------------------------------------------
videos/reels: bunny_id string nullable INDEXED (not unique), bunny_status

user_id ownership column. Models auto-generate slugs on save. No unique
constraints preventing duplicate content uploads.

11. QUEUE INVESTIGATION
--------------------------------------------------------------------------------
QUEUE_CONNECTION=database (.env:38; config/queue.php default database,
retry_after 90; redis retry_after 660 configured). ProcessVideo: skips
Bunny videos early (video_path empty guard, ProcessVideo.php:29-32);
CompressReel: only dispatched on the REEL FALLBACK path. Queues are NOT
involved in TUS byte transfer. Queue config cannot cause the same-video
failure. NOTE: without a running queue worker cron, fallback reels and
legacy jobs stall - operational risk on cPanel, not this bug.

12. FALLBACK UPLOAD
--------------------------------------------------------------------------------
Triggered ONLY from frontend catch block after bounded TUS retries, when
prepData exists. POST videos|reels/direct-upload ->
DirectUploadController -> UploadService::uploadVideoDirect/uploadReelDirect:
loads EXISTING row by id+user_id, PUTs bytes to existing bunny_id. Creates NO
new Bunny video => no duplicates possible. Reachable: YES (both pages).
Caveat: uploadVideoDirect uses file_get_contents (whole file in memory);
reel variant writes local copy first. Fine for moderate sizes; large files
subject to PHP upload_max_filesize/post_max_size on cPanel.

15. SECURITY
--------------------------------------------------------------------------------
Auth: prepare-upload, tus-proxy group, thumbnails, status, direct-upload all
behind auth. Ownership checks on thumbnail/status/direct (user_id match).
TUS signature SHA256(lib+key+exp+guid), 24h expiry; raw API key NEVER sent to
browser (derived signature only). Validation: title max255, category exists,
price numeric>=0, thumbnail image<=5MB, enums whitelisted. Rate limits:
throttle:upload 100/hour/user|ip. CSRF deliberately excluded for tus-proxy
(stateless signed protocol; exclusion verified working after fix).
Residual risk (low): PATCH /tus-proxy/{id} does not verify the GUID belongs
to the requester - exploitation requires knowing guid AND valid signature.

16. PERFORMANCE
--------------------------------------------------------------------------------
Chunk 2MB: mobile-friendly/resumable but through the proxy each chunk costs
a full PHP request round-trip (worker held briefly per chunk). Retry ladder
bounded. Playback fully CDN-offloaded (HLS/MP4/thumbnails/preview.webp).
Processing offloaded to Bunny encoders; FFmpeg only for legacy/local files.

17. SCALABILITY (honest assessment)
--------------------------------------------------------------------------------
IMPORTANT ARCHITECTURAL TRADE-OFF: unlike the old direct-TUS design, ALL
upload BYTES now transit the Laravel server (in+out bandwidth doubled).
10 users uploading ...... fine on typical cPanel/VPS.
100 users uploading ..... heavy: sustained ingress+egress + PHP worker churn;
                          recommend raising chunkSize to 5-10MB and/or Redis.
1000 users uploading .... NOT realistic through the proxy on shared cPanel;
                          would need direct-to-Bunny with signed CORS fix,
                          offload proxying, or a dedicated upload worker box.
Upload scalability != processing scalability: encoding scales via Bunny
(cloud); playback scales via CDN edge. The bottleneck is purely the proxy
hop's bandwidth/workers. Watching/liking/commenting remain cheap (cached).

18. ROOT CAUSE
--------------------------------------------------------------------------------
Q1 Why does re-uploading the same video while first processes fail?
   Backend does NOT fail it (nothing reused, nothing locked). The observed
   failure was frontend-state: input value not cleared so re-selecting the
   identical file fired no change event, plus possible double-execution and
   (for proxied attempts) the 419 CSRF block. All three defects located and
   quantified above.
Q2 Is chunking responsible? NO - chunk mechanics are standard TUS; failures
   traced to offset reconciliation bugs, not chunking itself.
Q3 Is /tus-proxy responsible? PARTIALLY, HISTORICALLY: the concept is sound
   and required for mobile Chrome CORS, but its implementation had real
   defects (blind 409 retry; missing bare-path CSRF exclusion producing 419
   on every create - reproduced live). Both corrected. Current implementation:
   sound.
Q4 Is QUEUE_CONNECTION=sync responsible? NO - it is set to 'database', and
   jobs are not in the upload byte path at all.
Q5 Keep TUS chunking? KEEP - resumability + mobile reliability depend on it;
   consider 5-10MB later purely as a proxy-overhead optimization.
Q6 Keep current proxy architecture? KEEP (with today's fixes deployed).
   Evidence: mobile Chrome cannot do direct cross-origin TUS reliably; proxy
   is the only architecture that works everywhere; 409/CSRF defects are now
   patched rather than structural.
Q7 Restore previous direct Bunny TUS? NO - it demonstrably broke on Android
   Chrome (CORS) which is the primary complaint demographic.
Q8 Smallest safest fix? ALREADY APPLIED (minimal diff): add 'tus-proxy' to
   CSRF exclusions; offset-aware 409 reconciliation + fail-safe 400; clear
   input.value in onVideoChange both pages; uploading re-entry guard; versioned
   local tus.min.js. Remaining action: deploy + reproduce once against
   production logs to confirm.
