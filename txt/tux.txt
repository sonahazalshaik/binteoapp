# BINTEO FINAL UPLOAD STABILITY FIX

I want you to implement the upload fixes based on the investigation report you generated.

IMPORTANT:
Do NOT redesign the upload architecture.
Do NOT rollback the whole upload system.
Do NOT remove TUS.
Do NOT remove chunking.
Do NOT change QUEUE_CONNECTION as part of this fix.
Do NOT introduce Redis, Horizon, Supervisor, or another queue server.

The goal is to make the CURRENT upload system reliable while preserving its architecture.

==================================================

==================================================

Keep:

   ↓

   ↓
/tus-proxy

==================================================

Do NOT remove TUS chunking.

Keep the current chunked upload implementation.

Initially keep:

Do NOT change the chunk size in the same implementation pass.

We may test 5 MB later as a separate experiment, but first make the current 2 MB implementation reliable.

Do NOT convert the upload to one huge request.

==================================================
3. FIX SAME-FILE RESELECTION
==================================================

Verify the actual onVideoChange() implementation in:

resources/views/frontend/videos/create.blade.php
resources/views/frontend/reels/create.blade.php

Select A
→ Remove/cancel A

→ Upload should start.

Do not only fix removeVideo().
The actual file-change handler must support same-file re-selection.

==================================================
4. PREVENT DUPLICATE UPLOAD STARTS
==================================================

Make sure startUpload() cannot run concurrently for the same upload attempt.

Prevent:

startUpload()
startUpload()
startUpload()

from creating multiple upload attempts.

Use a clear upload-state guard.

The guard must be reset correctly after:

- successful upload
- controlled failure
- cancellation/reset

Do not accidentally prevent the user from starting a completely new upload after the previous upload has finished or failed.

==================================================
5. NEW UPLOAD MUST ALWAYS GET NEW BUNNY ID
==================================================

This is extremely important.

When the user uploads:

Video A #1

and Bunny is processing it, then uploads:

Video A #2

the second upload MUST be independent.

Expected:

Video A #1
→ Local record #1
→ Bunny GUID 111
→ TUS upload session 111

Video A #2
→ Local record #2
→ Bunny GUID 222
→ TUS upload session 222

Do NOT reuse:

- previous Bunny GUID
- previous TUS upload URL
- previous TUS upload ID
- previous Upload-Offset
- previous upload object
- previous fingerprint
- previous upload state

Same filename must NOT mean same upload.

Verify this in:

app/Http/Controllers/Web/BunnyUploadController.php
app/Services/Frontend/UploadService.php
app/Services/BunnyStreamService.php

and the frontend upload state.

==================================================
6. TUS FINGERPRINT
==================================================

Verify the current fingerprint behavior.

The current system should create a fresh upload attempt for every new upload.

Preserve:

storeFingerprintForResuming: false

if that is already the current intended configuration.

Do not allow the second upload of the same file to accidentally resume/reuse the first upload.

==================================================
7. FIX 409 OFFSET HANDLING
==================================================

Keep the new offset-aware 409 recovery.

Do NOT restore the old behavior that blindly resends the entire chunk using Bunny's offset.

The correct behavior should be:

PATCH
→ Bunny returns 409
→ HEAD Bunny upload
→ read Upload-Offset
→ validate offset
→ compare with client offset
→ retry only the required data
→ continue upload

Handle these cases:

CASE A:
Bunny offset == client offset

→ retry the current chunk normally.

CASE B:
Bunny offset > client offset but still within the current chunk

→ send only the remaining part of the chunk.

CASE C:
Bunny offset >= end of current chunk

→ consider that chunk already stored and continue to the next chunk.

==================================================
8. BOUNDED RETRIES
==================================================

There must NEVER be an infinite 409 retry loop.

Use a strict maximum number of offset-recovery attempts per PATCH.

Use something reasonable such as:

MAX_OFFSET_RECOVERY_ATTEMPTS = 2 or 3

After the limit:

- stop retrying
- log the failure
- return a controlled error
- allow the existing fallback/error handling where appropriate

Do NOT create another Bunny video just because a PATCH receives 409.

==================================================
9. VALIDATE BUNNY Upload-Offset
==================================================

When performing HEAD recovery, validate:

Upload-Offset exists
Upload-Offset is numeric
Upload-Offset is an integer
Upload-Offset >= 0
Upload-Offset <= Upload-Length where known

If Bunny returns a suspicious value such as:

Upload-Offset: 2

DO NOT blindly retry forever.

Log the value and the related upload information.

Do not assume that "2" is valid or invalid without examining the actual upload state.
