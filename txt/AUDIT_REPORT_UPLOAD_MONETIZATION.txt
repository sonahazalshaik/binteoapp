CLIENT-FACING SUMMARY: DIRECT BUNNY CDN UPLOAD ISSUES
================================================================

PREVIOUS STATE (WORKING FINE):
- Direct TUS upload from browser -> video.bunnycdn.com/tusupload
- Architecture: prepare-upload creates video in Bunny, returns TUS params
  with endpoint = https://video.bunnycdn.com/tusupload
- Browser uploaded chunks directly to Bunny CDN via TUS protocol
- Server never touched video bytes (scalable, zero bandwidth cost)
- This was the "Fast Uploading" implementation verified in 
  SCALABILITY_FINAL_REPORT.txt (Section 1, Category: FAST UPLOADING)

ISSUES THAT EMERGED ON MOBILE (ANDROID CHROME):
1. CORS POLICY BLOCK: Browser blocked requests to video.bunnycdn.com
   - Error: "Access to fetch at 'https://video.bunnycdn.com/tusupload' 
     from origin 'https://binteodemo.of2on.org' has been blocked by 
     CORS policy"
   - Bunny dashboard "Allowed Domains" whitelist (binteodemo.of2on.org,
     binteoapp.com, localhost) DID NOT RESOLVE the issue
   - Root cause: Mobile Chrome strict CORS enforcement on cross-origin
     TUS OPTIONS/PATCH requests with custom headers

2. 409 CONFLICT ERRORS DURING CHUNK UPLOADS:
   - PATCH requests returned HTTP 409 (Conflict) with wrong offset
   - HEAD probe returned suspicious Upload-Offset: "2" (bytes)
   - Client treated 409 as fatal -> triggered server fallback loop
   - Result: Infinite CREATE + PATCH 409 retries, upload never completes

3. BROWSER CACHE SERVING OLD TUS.JS CLIENT:
   - Cached tus-js-client v3.0.0 without proxy endpoint config
   - Fixed with ?v=2 cache-buster on script tag

4. REVERB/PUSHER BROADCASTER CRASH:
   - RuntimeException: "Failed to create broadcaster for connection 'reverb'"
   - PUSHER_* env vars referenced commented-out REVERB_* vars (null)
   - cURL error 7 spam: "Failed to connect to localhost:8080"
   - Fixed: BROADCAST_CONNECTION=log, commented all PUSHER/REVERB vars

5. JS SYNTAX ERROR IN REELS PAGE:
   - Duplicate closing brace at line ~2855
   - Uncaught SyntaxError blocked upload initialization

6. FILE INPUT RE-SELECTION BUG:
   - After canceling file picker, selecting same file did nothing
   - Fixed: e.target.value = '' in onVideoChange handlers

FIXES APPLIED (ALL IN PRODUCTION):
A) Switched endpoint from direct Bunny to same-origin proxy:
   BunnyStreamService.php: 'endpoint' => url('/tus-proxy')

B) TusProxyController.php 409 auto-retry:
   - On 409: HEAD to Bunny for actual offset -> retry PATCH at
     correct offset -> return success to client (client never sees 409)

C) Cache buster ?v=2 on tus-js-client script tags (both pages)

D) Mobile MIME type fallback + e.target.value='' in create.blade.php
   and reels/create.blade.php

E) Removed duplicate brace in reels/create.blade.php

F) Disabled Reverb broadcasting in .env (BROADCAST_CONNECTION=log)

CURRENT STATUS:

- Need client to re-test in incognito mobile Chrome and share logs

1. VIDEO UPLOAD PROCESS
================================================================

FLOW OVERVIEW:
User Browser -> Alpine.js Form -> prepare-upload API -> Bunny 
Stream API -> TUS Upload (direct/proxy) -> Thumbnail -> Publish

STEP-BY-STEP:

[STEP 1] FRONTEND FILE SELECTION
File: resources/views/frontend/videos/create.blade.php
- Alpine.js component "videoUpload()" manages 3-step wizard
- onVideoChange() handles file input:
  * Mobile MIME fix: if file.type is empty, detects extension 
    (.mp4/.mov/.avi/.mkv/.webm/.3gp/.m4v) and sets type manually
  * Creates ObjectURL for instant preview
  * Auto-fills title from filename (skips generic names like 
    "video", "image", "1000xxxx")
  * Reads duration via <video> element metadata
    (handles Chromium Infinity-duration bug via seek trick)

[STEP 2] METADATA ENTRY
- Title, Category (required), Language, Location, Description
- Hashtag chips input (comma/space/enter separated)
- Cover thumbnail upload (optional)

[STEP 3] PUBLISH -> startUpload()
- Validates title + category before proceeding
- Shows SweetAlert2 loader with live speed/ETA

BACKEND PREPARATION:
Route: POST /videos/prepare-upload (throttle:upload middleware)
Controller: app/Http/Controllers/Web/BunnyUploadController.php
Service: app/Services/Frontend/UploadService.php::prepareUpload()

Actions performed server-side:
a) Validate inputs (title required max 255, category exists,
   visibility in:0,1, pricing_tier in free/premium/exclusive)
b) Create video placeholder in Bunny Stream:
   POST https://video.bunnycdn.com/library/{libraryId}/videos
   Payload: {title, collectionId}
   Returns: {guid} -> saved as video.bunny_id
c) Create local DB record:
   - status = draft|published
   - bunny_status = 'uploading'
   - slug auto-generated (Str::slug + random suffix if dup)
   - pricing logic applied (tier map: free=0, premium=1, exclusive=2)
   - is_premium only if user hasPremiumAccess()
d) Schedule support: schedule_date + schedule_time parsed in
   Asia/Kolkata timezone, converted to app timezone
e) Generate TUS signature:
   SHA256(library_id + api_key + expiration + video_id)
   Expiration = now + 24 hours
f) Notify subscribers (DB + broadcast + Firebase job)
g) Create AdminNotification entry
h) Return JSON: {success, video_id, bunny_id, tus:{endpoint, headers}}

TUS UPLOAD (Browser -> Bunny CDN):
Library: tus-js-client v3.0.0 (CDN with ?v=2 cache-buster)
Config:
- endpoint: url('/tus-proxy') [same-origin proxy, fixes mobile CORS]
- chunkSize: 2 MB
- retryDelays: [0, 3000, 5000, 10000, 20000]
- headers: AuthorizationSignature, AuthorizationExpire, VideoId,
  LibraryId (from backend)
- fingerprint: unique per attempt ('tus-unique-' + timestamp + rand)
- storeFingerprintForResuming: false

PROXY (app/Http/Controllers/TusProxyController.php):
- create(): forwards POST to Bunny /tusupload, rewrites Location
  header from /tusupload/{id} -> /tus-proxy/{id}
- patch(): forwards chunk; ON 409 CONFLICT:
  1. HEAD request to Bunny to get actual Upload-Offset
  2. Retries PATCH at correct offset automatically
  3. Returns final result to client (client never sees 409)
- head(): forwards HEAD status check
- options(): CORS preflight with full TUS header whitelist

POST-UPLOAD SUCCESS:
a) Thumbnail upload if selected: POST /videos/{slug}/thumbnail
b) Success toast -> redirect to Studio Dashboard

FALLBACK PATH (if TUS fails):
- Logs error to backend via /upload/log-error
- Automatic retry through server: POST /videos/direct-upload
  DirectUploadController -> UploadService::uploadVideoDirect()
  Server reads file and PUTs to Bunny library endpoint directly

STATUS POLLING:
GET /videos/{video}/status -> checks Bunny encodeProgress
- status 4 or progress >=100 => bunny_status='ready', published
- statuses 1,2,3 => processing
- 5,6 => error

LOCAL FALLBACK UPLOAD (non-Bunny legacy path):
VideoService::store() -> saves locally -> ProcessVideo job:
- FFmpeg extracts duration, generates thumbnail at 5s
- Transcodes HLS variants: 360p(800k), 720p(2500k), 1080p(5000k)
- Writes master.m3u8 playlist, marks status=ready

5. WATCHTIME LOGIC (MONETIZATION TRACKING)
================================================================

THREE TRACKING LAYERS:

LAYER 1 - SESSION TELEMETRY (AnalyticsService::pingVideo)
Table: video_watch_logs
Keyed by: (session_token, video_id, reel_id, date)
- Frontend pings every ~10 seconds with watch_increment
- watch_duration_seconds accumulates deltas (anti-cheat:
  only positive increments accepted, completion_percentage
  uses max() so rewind cannot reduce it)
- Works for guests AND logged-in users (user_id nullable,
  backfilled when user logs in mid-session)
Example log line produced:
"Telemetry: Video/Reel Watched {duration_added:10,
 total_watch_seconds:70, completion_percentage:63.61}"

LAYER 2 - SESSION DURATION (pingSession)
Table: user_sessions
- start/ping/end actions tracked per session_token
- duration_seconds = started_at.diffInSeconds(ended_at)
- Feeds platform-wide engagement metrics

LAYER 3 - USER PROGRESS + RETENTION MILESTONES
(updateWatchProgress)
Tables: watch_history + videos columns
Per logged-in user per video:
- progress_seconds, total_duration, is_completed,
  device_type, last_watched_at persisted
RETENTION COUNTERS on videos table:
- retention_25, retention_50, retention_75, retention_100
- Incremented exactly once per user when they FIRST cross
  each milestone (oldPercent < m && newPercent >= m guard)
- Guests tracked via session array to prevent double counting
TOTAL WATCH TIME:
- Video.total_watch_time incremented by validated delta
  delta = max(0, requested_progress - stored_progress)
  (prevents scrubbing inflation)

VIEW COUNTING (VideoService::show):
- Views increment inside app()->terminating() (post-response)
- impressions kept >= views_count invariant maintained
- Logged-in views also dispatch RecordVideoView job
  (device detection: Mobile/Tablet/Desktop regex on UA)

DAILY AD REVENUE ACCRUAL (recordAdImpression):
Table: video_earnings (per video per date)
- ad_impressions++ per impression event
- estimated_revenue += gs('per_impression_earn') default 0.005
This creates the daily revenue pool basis for creator payouts.

6. CREATOR MONETIZATION LOGIC (COMPLETE)
================================================================

STREAM A - PPV (PAY-PER-VIEW VIDEO SALES)
------------------------------------------
PRICING SETUP (upload/edit):
- pricing_tier enum: free=0, premium=1, exclusive=2
- Only premium/exclusive tiers carry a price
- Server enforces: is_premium=1 ONLY IF creator
  hasPremiumAccess() (active subscription plan)
- price stored as decimal on videos table

ACCESS RESOLUTION (VideoService::show priority order):
1. Owner always has access
2. PurchasedVideo record exists -> access
3. Tier 2 (exclusive): requires hasOttAccess()
4. Any tier + viewer hasPremiumAccess() -> access
5. Otherwise paywall shown with Razorpay checkout

PURCHASE FLOW (Razorpay India):
a) createVideoOrder():
   Razorpay order created: amount = price*100 paise,
   currency INR, receipt = getTrx(), payment_capture=1
   Session stores {order_id, video_id, amount} keyed by trx
b) purchase():
   - verifyPaymentSignature (HMAC check against secret)
   - Payment status must be 'captured'
   - Session cleared
   - PurchasedVideo row: buyer, video, owner, price, trx
COMMISSION SPLIT (the core creator earning):
   totalAmount      = video.price
   creatorPercent   = gs('ppv_creator_commission_percent')
                      [admin setting, default fallback 60]
   creatorComm      = total * percent / 100
   adminComm        = total - creatorComm
   -> VideoCommission row records full split audit trail
      {video_id, purchaser_id, creator_id, total_amount,
       admin_commission, creator_commission, trx}
   -> creator.balance += creatorComm (instant credit)
   -> Transaction ledger row: type '+', remark
      'video_ppv_commission', post_balance snapshot,
      charge column holds admin's cut for reporting
   - Firebase push to creator: "X just purchased your video"

STREAM B - AD REVENUE SHARE
-------------------------------------------
- Ad impressions recorded per video daily (video_earnings)
- estimated_revenue accrues at per_impression_earn rate
- Banner ads (slot1-4) + interstitial Ads served on pages
- Daily aggregation available via AggregateAnalyticsData
  command for payout batch runs

STREAM C - SUBSCRIPTION PLANS (PLATFORM LEVEL)
-----------------------------------------------
- Plans/OttPlan models drive hasPremiumAccess()/hasOttAccess()
- Creators can SET prices only while subscribed (plan gating)
- Plan purchases handled by PlanController (is_premium=1
  catalog browsing for buyers)

CREATOR EARNINGS VISIBILITY:
- Transaction table = complete ledger (+/- with post_balance)
- VideoCommission = per-sale split receipts
- VideoEarning = daily ad revenue per video
- Studio dashboard surfaces balances derived from these tables

WITHDRAWALS:
- WithdrawalsExport exists (admin export of payout requests)
- balance field on users is source of truth

ANTI-FRAUD NOTES IN CURRENT IMPLEMENTATION:
- Signature verification mandatory before crediting
- Commission credited only after captured payment verified
- Watchtime increments sanitized (positive-only, monotonic
  completion percentage)
- Session-token scoping prevents cross-video watch inflation
- Rate limiting on upload/payment initiation endpoints
