══════════════════════════════════════════════════════════════
  2. PAYMENT FLOW
══════════════════════════════════════════════════════════════

  User clicks "Pay"
       │
       ▼
  PaymentController (or PlanController, OttPlanController)
       │
       ├── Creates Deposit record (status: pending)
       ├── Redirects to gateway (Razorpay/Stripe/Manual)
       │
       ▼
  Gateway processes payment
       │
       ├── Success → Razorpay/ProcessController (IPN/webhook)
       │            → Updates Deposit (status: success)
       │            → Credits user wallet or activates plan
       │
       └── Failure → Returns error
                    → Deposit stays pending/rejected

══════════════════════════════════════════════════════════════
  ⚠  DO'S & DON'TS
══════════════════════════════════════════════════════════════

  ✅ DO's:
  • Keep Gateway/PaymentController and Razorpay/ProcessController
    exactly where they are — routes reference them directly.
  • Use DB::transaction for all financial operations.
  • Log all payment callbacks for debugging.
  • Use Deposit model for tracking all payments.

  ❌ DON'Ts:
  • DON'T move or rename Gateway controllers — routes break.
  • DON'T modify Razorpay IPN/webhook handling.
  • DON'T change deposit/withdrawal status flow.
  • DON'T remove existing gateway configurations.
  • DON'T bypass the Deposit model — it's the audit trail.
